# Agent Note: 面向模型的 jev_decide 工具（TypeSafe AI System One API）

Status: implemented

[English](2026-09-28-tool-jev.md) | 中文

## 问题

harness 需要机器原生决策——路由、排序、抽取、紧急度判断——在这些场景里，"LLM 提示词+解析"的往返既慢又贵又不可靠。fork 的自动化与分诊流程需要类型化、可供代码直接分支的答案，并附带对每个答案可信度的估计。

## 决策

新增 `packages/web/tool-jev`，暴露一个 `jev_decide` 工具：模型发送一个 state 加一组原子化问题（`choice` 从命名选项中选、`score` 按评分标准打分、`noul` 命题真伪判断），从 TypeSafe（Jev）System One API 收到带概率分布与校准置信度的类型化答案。

- API 密钥只在执行时从 `TYPESAFE_API_KEY` 读取；绝不进入 config、工具参数或日志。密钥缺失时调用以结构化错误失败，而不是悄悄禁用工具。
- `questions` 以 `{ name, type, instructions, criteria }` 数组传入，因为值 schema DSL 不支持按键映射 schema；`parseJevArgs` 补足 DSL 无法表达的约束（非空 state、名称唯一、按原语校验 criteria）。
- 响应的 `answers` 对象以 `answersJson`（无损字符串化 JSON）返回，使规范化取值保持在输出 DSL 要求的无损 JSON 子集之内。
- 工具之外还有两条姊妹路径：本地 stdio MCP server（`jev-mcp`）以 `mcp__jev__jev_decide` 暴露同一能力，以及官方 TypeSafe agent skill 供编写针对该 API 的自动化。当原生工具缺少环境密钥时，模型会自行降级到 MCP 路径——在端到端运行中已实际观察到。

## 备选方案

- 在插件代码里内联调用 System One API 而不做成工具：模型对这一能力不可见，也无法在对话中使用。
- 等上游实现：上游没有 TypeSafe 集成，而本地需求是即时的。
- 仅 MCP 集成：多一跳进程且无收益，还把能力藏进生成命名空间。

## 后果

- bundle 现在依赖一个外部决策 API；其可用性受 `timeoutMs`（默认 15 秒）约束，工具并发安全。
- 目录维护：工具加入目录生成器的 `TOOL_PACKAGES` 与双语 tool catalog；zh 侧为手工镜像（生成器只写 EN）。
- 在下一次 promote 之前，生产 profile 通过 profile patch 从开发 worktree 构建加载本工具；release 包含后，patch 条目切换到 workspace package。

## 测试

- `packages/web/tool-jev/tests/tool-jev.spec.ts`：7 个测试（解析规则、criteria 校验、名称唯一、注册、以打桩 fetch 的类真实调用）。
- 两次端到端，对真实 API，来自生产会话：模型调用了原生工具（deadline-risk state 上 noul 0.97）；更早一次无环境密钥的运行中降级到 MCP 工具（noul 0.83），两次均向用户综合了答案。
