# Agent Note: 受限的冷会话历史内存

Status: implemented

[English](2026-09-09-bounded-cold-session-history-memory.md) | 中文

## Problem

即使客户端只请求尾部分页，冷历史观察也会恢复并保留完整的已解码 Session 日志。因此，按数量限制的缓存可能保留多个大型日志，其合计常驻内存超过 Node.js 堆限制，导致 Web 后端终止，并使完整的会话目录显得不可用。

## Decision

[会话查询配置](../../../../packages/session-query/session-query/src/config.ts)默认保留一个未固定的已准备冷观察。已测量容量的部署仍可显式设置 `preparedSessionCacheSize`，活动租约仍会固定，直到其所有者释放它们。

[Session 客户端](../../../../packages/api/session-controller/src/client/sessions/session.ts)为普通 Session 的打开快照请求八条消息。后续分页继续使用 50 条消息的页大小，直接子代理记录在打开时也保持 50 条消息。

缓存规则限制普通历史打开之间保留的完整日志；较小的打开快照则分别限制首个可见页面投影和传输的记录。两条规则都不会更改持久化或写入已存储的历史。

## Alternatives considered

**提高 Node.js 堆限制。** 否决，因为这只会延迟终止，同时允许保留的冷日志随机器内存增长，并且会使正确性依赖启动器特定的进程标志。

**根据持久化修订估算按字节加权的缓存。** 否决，因为持久化修订不提供可移植的解码常驻内存成本，压缩文件字节也无法约束恢复后的对象图。数量为一的规则提供可预测的默认值，而不发布误导性的字节保证。

**禁用已准备观察复用。** 否决，因为重新打开当前冷 Session 会再次解码并恢复同一个完整日志。一个条目保留常见的复用路径，同时淘汰之前未固定的历史。

## Consequences

在默认配置下，依次导航多个大型冷历史时，最多保留一个未固定的完整已恢复日志，用跨 Session 缓存命中率换取受限的累积。新的冷打开在解码时可能与上一个条目暂时共存，并发活动租约可以超过配置数量，直到所有者释放它们。提高 `preparedSessionCacheSize` 的运维人员承担相应的完整日志内存成本。

普通会话从较小的首次响应显示最近尾部，并通过现有分页路径加载较旧消息。已存储的 Session 格式、事件顺序和历史内容保持不变。
