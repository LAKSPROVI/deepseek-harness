# Agent Note: Recovery of a restored reasoning effort

Status: implemented

[English](2026-08-31-restored-reasoning-effort-recovery.md) | 中文

## Problem

Web 会话会从最新的持久 `request/header` 恢复模型选择。适配器设置、发现结果或应用构建随后可能改变精确模型公布的推理强度。即使当前适配器已不再接受恢复出的强度，该值仍会进入下一次请求，导致 LLM 校验在提供方 I/O 之前拒绝该轮次。新元数据还可能让模型选择器不再显示推理强度控件，使会话无法通过选择同一路由来清除无效值。

## Decision

Host 在返回 `session.models` 以及接纳 `session.prompt` 之前解析精确模型元数据。如果所选推理强度不在当前模型公布的级别中，实时选择会采用当前 `defaultEffort`；若模型未公布默认值，则省略该字段并保留提供方默认行为。下一次模型请求通过普通 `request/header` 记录规范化后的选择，不改写早期事件。

无法解析精确模型元数据时，不改变提供方、模型或推理强度。现有的不可用路由响应因此保留用户选择的身份，并继续作为适配器被移除或暂时不可用时的恢复路径。

精确模型解析是异步的。如果陈旧推理强度的恢复仍在等待时另一个选择已被接受，较新的完整选择保持权威，延迟完成的恢复不会覆盖它。

## Alternatives considered

- **要求用户再次选择同一模型。** 选择器会把未改变的提供方和模型组合视为无操作，而且当前元数据可能完全移除推理强度菜单，因此该操作不能可靠清除无效值。
- **改写最新的 `request/header`。** 会话历史是仅追加的，而该 header 记录实际执行过的请求。为修复实时配置状态而修改它会破坏回放证据。
- **在 LLM runtime 中调整推理强度。** Runtime 正确拒绝不受支持的显式值。在那里静默调整会向所有入口隐藏调用方缺陷，并让 Web 目录报告的选择不同于实际分发的请求。

## Consequences

当恢复或选择的推理强度存在时，prompt 接纳会解析精确模型。这会重复最终调用准备也要执行的元数据工作，但能阻止无效实时选择进入轮次，并使目录、prompt 接纳和实际分发的请求保持一致。

在下一次请求追加 header 之前，规范化只存在于当前进程。若在新轮次之前重启，系统可能再次推导出旧值，但同一个接纳检查会再次修复，而不会让轮次失败。不可用模型保持不变，不会被替换为臆造的路由。

## Testing

`packages/host/apiproxy/tests/api-proxy-models.spec.ts` 覆盖两种情况：模型不公布任何推理级别时恢复出日志中的 `off`，以及模型当前默认值已变化时恢复出日志中的不受支持级别。后者通过 `session.prompt` 进入，并验证 `agent/request` 捕获的选择。
