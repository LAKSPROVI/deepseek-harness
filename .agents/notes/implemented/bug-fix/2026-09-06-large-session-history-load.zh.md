# Agent Note：大会话历史加载

Status: implemented

[English](2026-09-06-large-session-history-load.md) | 中文

## 问题

在 Web 客户端打开一个很大的会话时会阻塞数分钟。某位运维存档里最大的会话（一份 31 MB 压缩事件日志）实测需要 76 秒——机器负载高时 162 秒——才能返回一页 `PAGE_MESSAGES`（50）条消息的历史，因为宿主在分页时会为该页的每个 tool event 计算一个渲染视图。最初的修复（9 月 6 日，旧 apiproxy 客户端下的提交 `e5f8fa1be8` 与 `87f484f49b`）把 180 秒的加宽 unary 期限与 8 条首页配对；0.1.7 上游集成整体替换该客户端时两者一起丢失，本记录也随之消失。2026-10-01 的健壮性审计发现回归在 `packages/api/session-controller` 重新打开：打开路径再次请求完整的 50 条窗口。

## 决策

顶层会话（`this.address === undefined`）的 `doOpen` 以 `FIRST_PAGE_MESSAGES`（8）打开：即 `FIRST_PAGE_OPTIONS`——普通历史选项仅调低 `turnWindow` 下限——使最近的往来在数秒内渲染出来。`loadOlder()` 在滚动时仍拉取 `PAGE_MESSAGES`（50），`loadThrough()` 保持每页 200 条，subagent 首屏保持整页——这是一条较冷的路径，若干测试钉住了其确切请求形态。轮次对齐不变：每个窗口在 500 条上限内仍跨过至少两个 `turn/start`，且流的重连回放复用打开请求，因此顶层会话重连时也使用小窗口。原修复中加宽期限的那一半在 0.1.7 载体中没有对应物——该载体完全不施加按方法的超时；这个缺口作为单独的未完成工作（载体级 RPC 期限策略）记录在案，而不是再次无声丢失。

## 验证

`session.client.spec.ts` 将顶层打开的 follow 请求钉在 `minMessages: 8`（含一个专门的首页测试），并把 `loadOlder` 的分页钉在 50；subagent 打开的断言保持 50。三个请求形态规格（`session.client.spec.ts`、`manager.client.spec.ts`、`transport.client.spec.ts`）一同通过。

## 曾考虑的替代方案

- **改回旧的加宽期限而非页大小** — 拒绝：页大小直接攻击成本本身，而不是容忍成本；新载体中的超时改动是另一项影响面不同的工作。
- **对每一页都缩小 `PAGE_MESSAGES`** — 拒绝：这会给普通会话平白多加一次 `loadOlder` 往返而没有好处；只作用于首页的旋钮让常规分页保持不变。
- **subagent 首页也缩小** — 拒绝：subagent 打开路径更冷，若干测试钉住了其确切请求形态；收益在大会话所在的顶层会话列表上。
- **在宿主上惰性计算 tool event 视图，而非在分页时** — 推迟：这是对底层成本的正确长期解法，但涉及宿主与共享客户端 fold 如何划分工作的结构性改动，超出一个加载时回归的范围。

## 后果

一个很大的会话打开时会在数秒内显示其最近往来，而不是卡在整个尾页上。顶层会话现在总是要多花一次 `loadOlder` 才能看到第 9 条及更早的消息。底层的每页视图计算成本与大会话的冷启动全量解码不变——病态会话在冷宿主上仍可能占用很长的首页，惰性视图与按帧索引读取才是那时的深层补救。重新同步的教训记录于此：事故修复必须逐条对照幸存架构复核，因为整体替换客户端会无声地重新打开它携带的每一项修复。
